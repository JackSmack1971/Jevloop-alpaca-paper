Jev-loop Codex Skill Audit — September 22, 2026
I audited the main branch of JackSmack1971/Jevloop-alpaca-paper as a complete Codex Skill package, not merely as a Python trading application. I inspected the Skill/router metadata, references, implementation modules, execution adapter, calibration pipeline, validation script, tests, and eval corpus; compared those against the project control-plane engineering guides; and checked current OpenAI/Codex, TypeSafe/Jev, Vercel, Alpaca, Requests, uv, and relevant academic sources.
Executive assessment
The skill is already architecturally strong. The 0.3.1 work solved many of the obvious problems, and I would not respond to this audit by adding more instructions to SKILL.md.
The highest-value next release is a 0.3.2 evidence-and-runtime hardening release.
Your root Skill now matches OpenAI's current direction unusually well: minimal router, progressive disclosure, task-specific references, deterministic scripts for deterministic work, and no attempt to make prompt text an authorization boundary. OpenAI's September 2026 Astra guidance specifically recommends this pattern for multi-workflow skills. (OpenAI Developers) Your project architecture says the same thing: a Skill is knowledge/workflow/resources/dependencies, while policy/runtime—not Skill activation—authorizes effects.
The next weaknesses are lower in the stack:
The behavioral architecture is ahead of the evidence architecture.
I found several material runtime and evaluation defects that were not captured by the repository's existing validation report.

1. Prior-session orders should block paper mode
This is the most important new execution finding.
run() currently calls get_foreign_session_open_orders(). When old jevloop-* orders from a crashed or unclean prior process are found, the runtime prints a warning and continues.
That is safer than silently cancelling them, but not safe enough.
The current run's projected-position gate knows about:
text
broker position
+
this run's proposed order

It does not incorporate the potential future exposure represented by an old still-resting order.
For example:
text
current broker position:       $20
old session resting buy:       $25
new session proposed buy:      $25
max_position_usd:              $50

The new order independently appears admissible:
text
$20 + $25 = $45

but if both buys eventually fill:
text
$20 + $25 + $25 = $70

The session-local projected-risk calculation cannot guarantee its own position bound.
RECOMMENDED: keep the prohibition on automatically cancelling foreign-session orders, but make them a paper-readiness blocker:
text
dry execution:
    warn, continue

paper execution:
    foreign jevloop orders > 0
        → PAPER_PREFLIGHT_BLOCKED
        → no new orders

doctor should report the same condition as not ready.
This preserves your ownership boundary without silently accepting unknown outstanding exposure.
2. Move the doctor invariant into runtime
SKILL.md currently says:
Before paper orders, run doctor.
That's good behavioral guidance, but your own control-plane model correctly says behavioral instructions cannot provide hard enforcement.
A human—or another agent—can invoke:
bash
jev-loop run --paper

without first invoking doctor.
Some checks are repeated inside run, but there isn't one canonical readiness decision. In particular, the runtime and doctor can drift over time.
I would replace this with:
text
paper_preflight()
├── paper endpoint invariant
├── authenticated account read
├── account trading-blocked check
├── broker asset active/tradable
├── foreign-session order check
├── provider configuration sanity
└── result object + reason codes

Then:
text
doctor
    → displays paper_preflight()

run --paper
    → requires paper_preflight().ready

SKILL.md can then become even simpler: "run --paper performs mandatory paper preflight; use doctor to inspect readiness independently."
That converts an important prompt instruction into an executable invariant.
3. Malformed Jev responses can crash the loop
battery.validate_answers() assumes each individual answer is dictionary-like and calls .get() immediately.
If a provider returns something like:
json
{
  "direction": "up"
}

instead of:
json
{
  "direction": {
    "choice": "up",
    "probabilities": {}
  }
}

the result can be AttributeError, not ValueError.
The loop catches:
python
DecisionClientError
ValueError
KeyError
TypeError

but not AttributeError.
The same general issue exists if the outer response is JSON but not the expected mapping shape.
This matters beyond process cleanliness. If malformed output happens after the process already has resting paper orders, an unexpected exception can leave the normal cancellation path.
RECOMMENDED: introduce one schema-boundary error:
text
DecisionSchemaError

Validate explicitly:
text
response is mapping
answers is mapping
each expected answer is mapping
probabilities is mapping
exact keys correct
values finite
ranges valid
probability sum valid

Everything untrusted from the decision provider should fail into the same controlled ladder:
text
invalid provider response
        ↓
RULES_ONLY / HOLD_BLOCKED
        ↓
cancel + verify
        ↓
no new orders

Never let arbitrary Python container types determine control flow.
4. Unexpected exceptions need abnormal-exit reconciliation
The loop's structured shutdown handling mainly covers KeyboardInterrupt and _StopRequested.
An unexpected programming/data exception does not receive the same broker cleanup treatment.
The stronger invariant is:
text
any abnormal exit after paper authority has become active
        ↓
best-effort session-owned cancellation
        ↓
broker verification
        ↓
durable failure evidence
        ↓
nonzero exit

Do not swallow the original exception. Record both:
text
original failure
cleanup result

This turns failures into reconstructable evidence rather than Python termination.
The evaluation pipeline has a deeper provenance problem
The package's probability methodology is conceptually sound. Brier score and log loss are proper scoring rules; proper scoring rules are specifically designed for evaluating probabilistic forecasts rather than simply top-class accuracy. (Statistical Sites) Your skepticism toward vanilla ECE is also justified: Nixon et al. found calibration conclusions can change substantially with binning, top-label reduction, and class conditioning, and found adaptive/classwise approaches more stable. (arXiv)
The problem is which observations go into those statistics.
Real forecasts can currently acquire simulated labels
simulate and real operation append into the same logical evidence stream.
pair_observations() correctly skips a MOCK row as the forecast being evaluated by default.
But its future outcome search considers subsequent rows with mid and ts irrespective of whether that future price came from:
text
same real run
another real run
another model
a simulation
mock data

So the effective chain can be:
text
real Jev forecast at t0
        ↓
simulation row at t0 + 15
        ↓
synthetic price becomes "ground truth"

That invalidates the calibration observation.
The proper solution is not another warning. It is identity.
Log schema v3
I recommend every observation carry at least:
text
run_id
runtime_mode           dry-real | paper-real | simulation
data_source
package_version
git_commit
skill_digest
started_at

provider_model

decision_completed_at

Then pair only compatible observations:
text

same run/cohort
real pricing source
required freshness
target timestamp inside declared tolerance

This directly implements the project knowledge principle that executions need provenance, immutable identity, and reconstructable evidence rather than a pile of anonymous results.
Enforce label-lag tolerance
For a 15-second horizon, the current algorithm selects:
text
first observation timestamp >= t + 15

If the next sample is at:
text
t + 147 seconds

it becomes the 15-second outcome.
Add:
text
requested_horizon_seconds
actual_label_lag_seconds
max_label_lag_seconds

and discard unmatched forecasts.
Do not block-bootstrap an interleaved multi-symbol stream
Moving-block bootstrap works by resampling consecutive observations to retain time dependence. (OUP Academic)
The current calibration code creates labels within each symbol, then merges all observations by timestamp and block-bootstraps that combined sequence.
That can create blocks like:
text
BTC
AAPL
BTC
ETH
AAPL
...

which is not the serial process whose dependence you intended to preserve.
Either:
text
require --symbol for block-bootstrap CIs

or implement a symbol-stratified/hierarchical method.
The first option is much simpler and harder to misuse.
Your timeout contract is still overstated
The 0.3.1 change from a scalar timeout to:
python
(connect_timeout, read_timeout)

was an improvement.
But Requests explicitly documents that neither connect nor read timeout is a wall-clock timeout. Multiple address attempts can extend connection time, and read timeout describes socket inactivity, not an overall request deadline. (Requests)
So _post() should not imply its deadline is a guaranteed transport deadline.
At minimum:
text
request returns
      ↓
measure actual elapsed monotonic time
      ↓
elapsed > deadline
      → discard otherwise-valid answer
      → HOLD_LATE

For a true wall-clock cancellation guarantee, the transport architecture needs to support an actual outer cancellation/deadline mechanism. Tweaking Requests' two timeout numbers alone cannot provide that contract.
Evidence should capture provider correlation IDs
Alpaca currently documents X-Request-ID on Trading API responses and recommends persisting recent IDs because they cannot be retrieved later. (Alpaca US) Market Data has the same recommendation. (Alpaca US)
Your _request() currently reduces a response to JSON/body and loses that evidence.
For an ambiguous order submission, a high-quality evidence record should be able to connect:
text
local run_id
client_order_id
POST X-Request-ID
reconciliation GET X-Request-ID
order_id
subsequent cancellation request IDs
final broker state

That dramatically improves postmortem quality.
Alpaca also continues to recommend streaming updates for maintaining order state, and trade_updates contains fills, partial fills, cancellations, and rejections. (Alpaca US) I would not make WebSockets a 0.3.2 requirement, however. The current REST model can be hardened first; streaming introduces reconnect, ordering, backfill, and gap-recovery requirements of its own.
One Codex design choice should change
I would reconsider:
yaml
policy:
  allow_implicit_invocation: false

OpenAI documents this flag as Skill invocation policy: false prevents Codex from automatically selecting the Skill, while explicit $jev-loop invocation still works. (OpenAI Developers)
It is not a broker authorization boundary.
Your own architecture correctly establishes:
text
skill activation ≠ permission

and the package already has stronger effect controls:
text
default = dry
paper requires --paper
mock cannot submit
live endpoint impossible
Codex policy still controls tools/network

So using explicit-only Skill selection because the package might eventually perform a paper effect conflates selection with authorization.
It also creates a direct inconsistency with evals/routing.jsonl: that corpus spends substantial effort evaluating whether prompts should implicitly activate jev-loop, while production metadata tells Codex not to do that.
Recommended invocation architecture
I would use:
yaml
allow_implicit_invocation: true

and keep:
text
implicit skill activation
        ≠
paper authorization

paper side effect
        requires
explicit user intent
        +
--paper
        +
runtime preflight
        +
effective Codex execution/network policy

That is the cleaner control-plane design.
If you deliberately want $jev-loop to be mandatory for UX reasons, keeping false is legitimate—but then the routing corpus should stop pretending implicit activation is a production behavior.
The Skill eval suite needs to become executable
This is probably the single biggest Skill-level improvement.
Your eval files currently describe expected behavior, but validate_package.py mostly verifies:

Then run Skill vs no-Skill paired evaluations.
That is how you learn whether the package itself adds value rather than whether Codex is already smart enough to solve the task.
OpenAI's current guidance is explicit that evals are the reliable way to distinguish actual Skill improvement from merely changing behavior. (OpenAI Developers)
Reproducibility is incomplete without uv.lock
This should be fixed now.
The repository has version ranges in pyproject.toml but no lockfile.
uv's current official documentation says uv.lock contains the exact resolved dependency versions and should be committed to version control for reproducible installations. (Astral Docs) uv lock --check / uv run --locked then provide an enforceable stale-lock check. (Astral Docs)
I would therefore make:
text
uv.lock

required by validate_package.py, then add CI.
The current repository tree contains no GitHub Actions workflow, so the excellent local validator is not currently a merge gate.
Research conclusion on the statistical layer
I would not spend the next release adding more financial metrics.
The methodology already correctly emphasizes:
text
Brier + log loss
calibration diagnostics
serial-dependence-aware uncertainty
chronological OOS evaluation
selection/multiple-testing control
negative results
economic materiality separate from statistical evidence

The academic basis is good. Proper scoring rules are the right foundation for probabilistic predictions. (Statistical Sites) ECE deserves the skepticism already present in the package. (arXiv) And if/when strategy selection becomes a claim, Deflated Sharpe Ratio correctly addresses selection bias, multiple testing, and non-normal returns rather than treating the best observed Sharpe as pristine evidence. (SSRN)
The bottleneck is now provenance and cohort integrity, not statistical sophistication.
Fixing which observations are eligible is worth far more than adding a fifth calibration statistic.
Provider-contract research status
The core provider documentation in the Skill is current as of today.
TypeSafe's live OpenAPI currently exposes bearer-authenticated POST /v1/systemone and GET /v1/models, matching the package. (Typesafe API) Vercel's September 21 update confirms that existing TypeSafe/SystemOne calls can be pointed at AI Gateway without changing evaluation shape, while new HTTP integrations can use /v1/evaluate; the current model identifier is typesafe-ai/jev. (Vercel)
The Skill also correctly treats probability calibration as something to establish empirically on its own workload rather than accepting vendor performance/calibration claims as evidence.
Recommended 0.3.2 scope
I would make the next release one coherent hardening unit:
1. Runtime authority/effect boundary: shared automatic paper preflight; foreign-session orders block paper mode; malformed-provider responses become typed failures; unexpected process failures perform verified cleanup.
2. Evidence schema v3:run_id, mode/source, package/Git identity, provider/model identity, quote/trade timestamps, config digests, and external request IDs.
3. Calibration isolation: simulation separated by default; same-cohort labels only; freshness + maximum-label-lag requirements; symbol-safe bootstrap inference.
4. Codex Skill behavior: enable implicit invocation, shorten the routing description slightly, leave the root router otherwise lean, and update eval semantics accordingly.
5. Executable Skill evals:codex exec --json, deterministic graders, paired Skill/no-Skill runs, raw trace retention.
6. Reproducible engineering: commit uv.lock; add CI for uv lock --check, locked sync, Ruff, tests, package validation, and compile checks.
7. Architecture cleanup: extract a pure tick-decision/reducer layer shared by real operation and simulation so simulate.py cannot silently diverge from production control logic.
The architecture references strongly support exactly this direction: immutable identity/versioning, progressive disclosure, deterministic scripts, explicit provenance, and the rule that Skill activation can never expand authority.
Verification status
This was a source-level repository audit plus current external research. I inspected main directly through GitHub. I did not independently execute the repository test suite in this audit environment, so the repository's existing statement that 88 tests pass remains historical repository evidence, not a fresh test result from me.
The package's previous 0.3.1 audit was valuable, but I would not stop there. The issues above justify a 0.3.2 release before spending effort on additional strategy sophistication or UI work.
The highest-value implementation order is: paper preflight/foreign-order blocking → typed provider failures + abnormal cleanup → evidence schema/calibration isolation → executable Codex evals → lockfile/CI.
